# 1. Add Conventional Commits and Changelog Generator

### Date

2026-09-10

### Status

Accepted

### Context

We need a reliable and repeatable release-note workflow for this repository. Currently, changelogs are generated by hand there is no commit message linting or validation. This makes it difficult to automate changelog generation and enforce a consistent commit style.

Before this change, changelog updates and commit style relied on manual discipline, which made entries inconsistent and harder to automate.

### Decision

Adopt [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) as the required commit format and automate changelog generation from commit history. It will still be a human decision to determine if the version is a major, minor, or patch release, but the changelog will be generated automatically from the commit history.

The GOV.UK way of working does create a large volume of commits. Not all of these need to be represented in the changelog. The `changelog` tool will skip commits that fail the conventional commit format check. We will leverage this to ensure that only meaningful commits are included in the changelog, while still allowing for smaller, less significant commits to be made without cluttering the release notes.

Implementation choices:

- Conventional Commit tooling (`@commitlint/cli` and `@commitlint/config-conventional`)
  - Allows us to define linting rules for commit messages and enforce them at commit time
  - Allows us to generate changelogs automatically from commit history
  - Allows us to use commit messages to drive semantic versioning in the future
  - Allows smaller commits to be skipped from changelog generation if they do not follow the Conventional Commit format
- A commit-message lint config in `commitlint.config.js`
  - Defines the rules for commit message validation
  - Allow customization of rules in the future if needed
- Add a github workflow to run commitlint on pull requests
  - Ensures that at least one commit in a PR follows the Conventional Commit format before merging
  - Forces developers to inclulde at least one meaningful commit in a PR, which will be included in the changelog
- Changelog generation tooling (`conventional-changelog*` packages)
  - Allows us to generate changelogs automatically from commit history
  - A `changelog` npm script and a `version` script that regenerates `CHANGELOG.md`
  - Automates the process of generating and updating the changelog during version bumps
  - Allows us to keep the changelog up-to-date with each release
- Use `@commitlint/config-conventional` as the baseline ruleset, this defines:
  - Commit types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, and `revert` see [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) for details
  - Commit message format: `<type>(<scope>): <subject>` with optional body and footer
  - Scope is optional, but recommended for larger changes to indicate the area of the codebase affected by the change
- Generate `CHANGELOG.md` via `conventional-changelog`
  - The layout of the changelog will adhere to the [Angular preset](https://github.com/angular/angular/blob/main/contributing-docs/commit-message-guidelines.md/), which is widely used and recognised
  - The changelog is generated in a consistent format that is easy to read and understand
  - The changelog can be regenerated at any time to reflect the current state of the repository
  - The change log will be updated automatically during version bumps, reducing the risk of forgetting to update it manually
- Regenerate and stage changelog updates during `npm version` via the `version` script
  - KISS – Keep It Simple Stupid – the changelog is updated automatically during version bumps, reducing the risk of forgetting to update it manually.

This keeps day-to-day commit validation local to contributors and makes release documentation deterministic.

### Consequences

- Positive impacts:
  - Produces consistent commit messages that are easier to scan and search
  - Enables automated, repeatable changelog generation with less manual editing
  - Reduces release overhead and risk of missing notable changes
  - Balances the need for small, frequent commits with the need for meaningful changelog entries
  - Changelog entries can be richly formatted with links to PRs, issues, and contributors as needed.
    - e.g. - Fixes a bug in the widget [[abc1234567](https://github.com/alphagov/content-block-picker/commit/abc12345670ec9b279462fe3e9b81f04c80344de)], John Doe at 01/01/1970
- Negative impacts or trade-offs:
  - Contributors must learn and follow Conventional Commit format
  - Commits can be blocked locally until message format is corrected
  - Tooling adds maintenance overhead (Husky/commitlint/changelog dependencies)
- Future implications:
  - We can expand release automation (for example, semantic versioning pipelines)
  - Commit message conventions become part of contributor onboarding and documentation

**Rejected options:**

- Continue with manual changelog maintenance only: rejected due to inconsistency and increased release-time effort.
- Build a custom commit parser/generator: rejected because mature ecosystem tools already solve this with lower maintenance cost.
