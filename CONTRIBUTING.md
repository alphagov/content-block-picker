## Changelog 

The change log is auto-generated from the commit history. The release process is covered in the [release process section of the README](README.md#release-process).

### Conventional commits

The GDS way of working splits work down into small atomic changes. This would lead a bloat in the changelog that would be unhelpful to the reader. To avoid this, we use a workflow that allows the author to specify only certain commits get included in the changelog. We leverage the way the `conventional-changelog-conventionalcommits` parser works to exclude some commits from the change log. Commits that do not follow that pattern will be ignored. ### Workflow

We include a workflow that will parse the commits in a given PR and will reject that PR if there is not at least one commit that matches the conventional-commits format. This ensures that all PRs will have at least one commit that will be included in the changelog. The workflow is defined in `.github/workflows/pr-title-parser.yml` and is triggered on `pull_request` events. It uses a custom action to parse the commits and check for the conventional-commits format. If no matching commits are found, the workflow will fail and the PR will be rejected. This workflow will skip this check if the PR is raised by one of the automated bots (dependabot, renovate, etc.) as these PRs are not expected to have any conventional-commits formatted commits.

The workflow calls a JavaScript script that will parse the commits in the PR and check for the conventional-commits format. The script is defined in `bin/lint-pr-commits.js` and uses a node script to parse the commits. The script will check each commit message against the conventional-commits and if no matching commits are found, the action will fail and the workflow will be rejected.

This script can be run locally by running `node bin/lint-pr-commits.js <BASEREF> <HEADSHA>`. The script will fetch the commits for the given PR number and check for the conventional-commits format. If no matching commits are found, the script will exit with a non-zero status code.

### Generating the changelog

The changelog is auto-generated from the commit history using the `conventional-changelog` package. The changelog is generated by running the `npm run version <major|minor|patch|x.y.z>` command. This command will generate a new version of the package and will rebuild `CHANGELOG.md` from scratch using the commits that match the conventional-commits format. Because it overwrites the managed changelog instead of prepending to it, rerunning the command does not duplicate entries.

```
npm run changelog
```

### Releasing a version

The release process is covered in the [release process section of the README](README.md#release-process). The release process will generate a new version of the package and will rebuild `CHANGELOG.md` from scratch using the commits that match the conventional-commits format. Because it overwrites the managed changelog instead of prepending to it, rerunning the command does not duplicate entries. It will also create a new git tag for the version and commit to the repo, ready to be pushed as part of the PR.

e.g. Create a patch release and update the changelog:

```bash
npm version patch
git push --follow-tags
# raise the PR for the release
# when merged to main, run the 'Publish to NPM' action in GitHub Actions.
```
